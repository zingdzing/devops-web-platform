# Phase 0-1 真实问题记录

本文只记录实际发生并完成验证的问题，不包含密码、私钥、公钥正文、验证码或恢复码。

### SSH Agent 未加载受口令保护的密钥

**现象：** 非交互式环境执行 `git push` 时无法完成 SSH 身份验证。

**影响：** 本地提交不能推送到 GitHub。

**证据：** 用户在自己的 WSL 终端启动 `ssh-agent` 并执行 `ssh-add ~/.ssh/id_ed25519` 后，同一仓库的 `git push -u origin main` 成功。

**根本原因：** 私钥受口令保护，新的终端会话没有已解锁密钥，自动化进程也不能代替用户输入口令。

**解决办法：** 在用户终端执行 `eval "$(ssh-agent -s)"` 和 `ssh-add ~/.ssh/id_ed25519`，由用户本地输入口令。

**验证结果：** GitHub 接收新 `main` 分支，远程跟踪关系建立。

**预防措施：** 推送前用 `ssh-add -l` 检查 Agent；永远不把口令或私钥交给脚本、聊天或仓库。

### Windows 暂存文件获得错误的可执行权限

**现象：** 从 Windows 暂存区复制的普通文本文件在 Git 中显示为模式 `100755`。

**影响：** Git 提交把非脚本文件标记为可执行，降低仓库整洁度。

**证据：** `git diff --summary` 与提交内容显示普通文件模式为 `100755`，归一化后显示 `100644`。

**根本原因：** Windows 与 WSL 文件权限语义不同，跨文件系统复制时可执行位不能按项目意图自动判断。

**解决办法：** 普通文件设置为 `chmod 644`，需要直接执行的 Bash 脚本设置为 `chmod 755`，再创建提交。

**验证结果：** Git 中普通文档和代码为 `100644`，验收脚本为 `100755`。

**预防措施：** 提交前执行 `git diff --summary` 和 `git diff --cached --summary` 检查模式变化。

### ShellCheck SC2034 报告未使用的循环变量

**现象：** 等待循环声明了变量，但循环体从未读取它。

**影响：** ShellCheck 阻止脚本通过静态检查。

**证据：** ShellCheck 返回 SC2034；把变量改为 `_` 后告警消失。

**根本原因：** 循环只需要控制重试次数，不需要使用当前计数值。

**解决办法：** 使用 `for _ in {1..90}` 明确表达“忽略当前值”。

**验证结果：** Bash 语法检查和 ShellCheck 均通过。

**预防措施：** 编写等待循环时，如果计数值无业务意义，直接使用 `_`。

### 缺少本地 `.env`

**现象：** Phase 1 启动脚本检测不到 `.env` 并主动退出。

**影响：** MySQL 和 Flask 无法获得本地数据库配置。

**证据：** 复制 `.env.example` 为 `.env` 后，启动和验收继续执行；`git status` 不显示 `.env`。

**根本原因：** 仓库只提供安全模板，真实本地配置按设计被 `.gitignore` 排除。

**解决办法：** 执行 `cp .env.example .env`，只在本地修改需要的值。

**验证结果：** Phase 1 MySQL 启动成功，完整 CRUD 验收通过。

**预防措施：** README 的首次启动步骤必须包含复制模板，并持续扫描 Git 跟踪文件中的敏感内容。

### ShellCheck SC2329 误判 trap 调用的 cleanup

**现象：** `cleanup` 函数只通过 `trap` 间接调用，ShellCheck 报告函数似乎未使用。

**影响：** 静态检查失败，但删除 cleanup 会失去验收后的资源恢复。

**证据：** `trap cleanup EXIT` 明确存在，运行验收时 cleanup 实际执行；仅 SC2329 仍出现。

**根本原因：** 静态分析不能在该写法下可靠追踪 trap 的间接函数调用。

**解决办法：** 保留函数和 trap，在函数前增加仅针对 SC2329 的 suppression，并写明原因。

**验证结果：** ShellCheck 通过，脚本退出时临时资源仍被清理。

**预防措施：** 只对确认的误报做最小范围 suppression，不使用全文件忽略。

### PowerShell 提前解释 WSL Bash 变量

**现象：** 从 PowerShell 传递包含 Bash 变量或复杂引号的命令时，参数被外层 Shell 改写；一次 MySQL 检查因此使用了错误的连接参数。

**影响：** 命令失败，输出不能代表应用真实配置。

**证据：** 在 WSL 内使用明确的本地测试变量重新运行后，MySQL 验证通过。

**根本原因：** PowerShell、`wsl.exe` 和 Bash 具有不同的引号与变量展开规则。

**解决办法：** 复杂逻辑写入版本化 Bash 脚本并在 WSL 内执行；临时检查尽量使用原子命令和明确参数。

**验证结果：** 使用 WSL 内部命令后，Phase 1 数据库测试按预期通过。

**预防措施：** 避免在 PowerShell 字符串中嵌套 Bash `$()` 和多层引号；失败后拆分命令确认参数边界。
